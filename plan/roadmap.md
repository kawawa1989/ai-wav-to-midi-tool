ステータス：計画策定済み／実装・PoC計測は未着手。対象環境：Mac（Apple M5、ユニファイドメモリ24GB）。
開発・初期運用は個人・非商用／無料ツール優先。ただしMuScriptorモデル重みには**非商用制限に加えて「入力音源の権利保証」条項**があるため、Phase 1着手前に入力素材の扱いを確定する（§7.1 R4/R5）。Phase 5で商用化する場合は別途ライセンス審査を必須とする。

# 1. プロジェクトの目的・到達点

**アウトカム定義:**

- 任意の楽曲のローカル音声ファイル（MP3/WAVなど）を入力し、楽器別の編集可能なMIDIと、全パートをまとめたバンドスコア（MusicXML / PDF）を生成できる。
- 耳コピ・パート分解・MIDI入力の工数を下げられる状態にする。
（原曲を完全に再現できるとは限らないため、検証・修正できることを要件に含める。）

**品質への期待値（v1.1で追加）**：MuScriptor largeの公表Multi F1は48.2（開発元の自己申告）。密なバンドサウンドでは**半分程度は手修正する前提の「下書き生成ツール」**として位置づける。

**スコープを2段階で区別**：

- 変換の成功:
    - 音声から全曲の複数楽器トラックを持つ有効なMIDIを生成し、MusicXML・PDFに変換できる。
- 採譜の品質:
    - 音程、音価、演奏タイミング、楽器分類、テンポ・変拍子、奏法・TABの妥当性。
    こちらは別途評価し、必要ならユーザーが修正する。

# 2. 決定済みの要件と前提

## 2.1 機能要件（FR）

- **FR-01 入力**：最初は手元に権限のあるローカルMP3/WAV。複数の音声フォーマット対応は後続Phaseで拡大。YouTube URLの自動ダウンロードは対象外。
- **FR-02 複数楽器の自動採譜**：ギター、ベース、ドラム、キーボードを優先。ボーカルは対象外。楽器推定と手動楽器指定を切り替え可能にする。楽器分類はモデルの36グループに従う。**同じグループに入る複数パート（ギター2本など）の分離はFR-11で扱う。**
- **FR-03 パート別MIDI**：楽器名、MIDIプログラム、チャンネル、ノートの開始・終了時刻／ピッチを保持したマルチトラックMIDI（SMF）を出力。ドラムはGMマッピングを検査し、**打点のみ（音価なし）**として扱う。
- **FR-04 テンポ・拍子**：テンポマップ、拍子、ダウンビート、量子化グリッドの推定と手動補正。変拍子曲を想定し、**小節範囲ごとに拍子を指定できるメーターマップ設定**を持つ。テンポの倍/半分の誤検出は手動補正で直せるようにする。
- **FR-05 楽譜**：MusicXMLと全パートPDFを出力。
- **FR-06 二種類のMIDI**：未量子化の演奏タイミングを重視した raw.mid と、楽譜向けに量子化した score.mid を分ける。音符情報を不用意に上書きしない。
- **FR-07 ユーザー補正**：各パートの有効／無効、ノート修正、テンポ・拍子、トラック名、誤検出箇所を保存して再出力（初期はMuseScore等を外部エディタとして使う）。
- **FR-08 比較・診断**：原曲とのA/B試聴、抽出トラック一覧、音符数、欠落楽器、出力エラーと実行ログを記録。
- **FR-09 バッチ変換**：最終的にはフォルダや複数ファイルを対象に、同じ処理を再現可能に実行できる。
- **FR-10 再現性**：実行モデル、**モデル重みのrevision（Hugging Faceコミットハッシュ）**、MuScriptor／MuseScoreのバージョン、uv.lock、設定、入力ファイルハッシュ、処理日時を保存。
- **FR-11 同種楽器の分離（v1.1で追加、Phase 3）**：同じ楽器グループにまとまったパートを分けたい場合、音源分離またはステレオ定位（L/R・Mid/Side）で分けた音声を再採譜して別トラック化する。自動分離は保証しない。

## 2.2 非機能要件（NFR）

- **NFR-01 費用**：Phase 1〜4は有料サブスクリプションを使わずローカル実行を基本とする（電力、ストレージ、ダウンロード通信、人の修正コストは発生する）。
- **NFR-02 環境**：Apple M5 / メモリ24GBのmacOSで動作。Metal/MPSを使い、メモリ不足時はmedium/smallへ自動または手動で切り替える。
- **NFR-03 プライバシー**：音源をクラウドへ自動送信しない。ユーザーの明示操作なしにアップロード・共有しない。ローカル処理と削除手段を提供する。MuScriptorはローカル版（CLI／`muscriptor serve`）のみ使い、ホスト版Webアプリには音源を送らない。
- **NFR-04 信頼性**：処理失敗時に原因と回復手段を表示。途中ファイルとログで再実行・診断ができる。
- **NFR-05 拡張性**：採譜モデル、音源分離、譜面生成を交換可能にする。ただし境界の切り出しは必要になった時点で行う（ADR-02）。
- **NFR-06 権利保護**：処理する原曲の利用権限と、公開／配布するMIDI・スコアの権利を区別する。非商用モデル重みの制約と、入力音源の権利保証条項を常に明示する。
- **NFR-07 速度**：まずM5実機で30秒／3分／6分の入力を計測してベースラインを定める。根拠のない秒数SLAを先に設定しない。

## 2.3 現時点の非対象

- 原曲との完全一致の保証、原曲の音色を再現した高品質音源生成、全ギター奏法の自動TAB確定。
- 同じ楽器グループ内の複数パートの完全自動分離。
- ベロシティ（強弱）の推定。モデルが出力しないため、固定値を入れる場合は「推定値ではない」と明示する。
- Webサービス公開、課金機能、複数ユーザー認証、クラウド常時推論、YouTubeからの無断ダウンロード。
- 独自基盤モデルの学習。最初は既存モデルの比較・組み込みを優先。

# 3. 技術調査・採用方針（2026-10-25時点）

## 3.1 重要な結論

- **PoCから自動化まで一貫してMuScriptor（CLI／Python）を使う**：`uvx muscriptor transcribe` で採譜し、`--model`、`--quantize`、`--grid`、`--bpm`、`--beats-per-bar`、`--first-downbeat`、`--fixed-tempo` などで補正する。GUIで目視確認したい場合はローカルの `muscriptor serve` を使う。
- **NeuralNote v2は不採用（任意の参考）**：中身は同じMuScriptorで、CLIは未提供、楽器別チャンネルのMIDI出力もまだロードマップ項目。DAWプラグインとして使いたくなった場合に再検討する。
- **MuScriptorは単体でMIDI、量子化、拍子・テンポ推定、MusicXML、全パートPDF、楽器別PDF・TAB譜を出力できる**。譜面出力にはMuseScore 4以降が別途必要（`$MUSCRIPTOR_MUSESCORE` で場所を指定可能）。MVPではこれを再利用し、既存機能を重複実装しない。
- **モデルの制約（モデルカードより）**：
    - 入力は16kHzモノラル、5秒チャンクで処理する。
    - 楽器は128のMIDIプログラムを36グループに分類する（`muscriptor list-instruments` で確認）。
    - 同じ楽器・同じ音程のノートを同時に表現できない（ユニゾンやダブリングは欠けやすい）。
    - ドラムは打点のみ。ベロシティは出力しない。
    - 密なミックス、特殊な音色、強く加工された音で誤りが増える。オフセットはオンセットより不正確。
    - テンポが倍/半分に誤検出されることがある。ルバートは苦手。
- **モデル選択**：mediumが既定、largeが最高品質。M5実機で速度・ピークメモリ・品質を比べて決める。largeの常用を決め打ちしない。
- **代替手段**：Basic Pitchは主に単一楽器や分離済みステムの再採譜候補。Demucsは音源分離の候補だが、公式の旧リポジトリは保守終了で、6stemのギター／ピアノ分離にはアーティファクトの懸念がある。v1.1では**FR-11（同種楽器の分離）の主対策**としてPhase 3で評価する。最初から前処理を必須化しない。

## 3.2 技術スタック（暫定決定）

- 言語：Python。パッケージ・依存管理はuv（uv.lockで固定）、CLIはTyper等の軽量構成。
- 主採譜エンジン：MuScriptor（MacのMPS対応）。重みはHugging Faceのゲート付きリポジトリから取得（アカウント作成とライセンス同意が必要）。
- 楽譜生成：MuScriptor + MuseScore Studio 4以降。出力はMusicXML、PDF、TAB-PDF、MIDI。
- MIDI処理：pretty_midi または mido を比べて選ぶ。拍子処理・MusicXML加工が必要なら music21 を検討。
- 評価：mir_eval（モデルカードの公表値と同じ指標系）。正解音源の生成にはFluidSynth等のMIDIレンダラーを使う。
- ビート／ダウンビート推定（Phase 3で比較）：MuScriptor内蔵の推定 vs 外部モデル（beat_this等）。
- オーディオ：デコード／リサンプリング／区間切り出しを標準化。FFmpeg導入は使用条件と環境依存を確認する。
- 分離エンジン：Phase 3で費用・保守性・精度から採否を決める。
- UI：Phase 1〜2はCLI＋MuseScore（必要に応じて `muscriptor serve`）／Phase 3で簡易ローカルUIを判断。
- ソース管理：Git。CIは音源を含まない小さなテスト素材を使う。

## 3.3 設計上の決定（ADR）

- **ADR-01 ローカルファースト**：音源と生成結果は原則Macのローカルディスクで管理する。
- **ADR-02 最小限のアダプター分離（v1.1で改訂）**：MVPでは **Transcriber（MuScriptor呼び出し）／Validator／JobRunner** の3境界だけにする。BeatGrid・MIDIProcessor・ScoreExporter・AudioLoader・Separatorは、Phase 3で独自処理が必要になった時点で切り出す。
- **ADR-03 中間表現を保存**：音符イベント（instrument_group, program, pitch, onset_sec, offset_sec=ドラムではnull, velocity=null, source_model, model_revision）、拍・テンポ・メーターマップ、メタデータを内部JSONとして保存する。モデルが出さない値（ベロシティ、ドラムの音価）を推定値として扱わない。
- **ADR-04 MIDIは一次成果物、譜面は派生成果物**：raw MIDIは未編集の原本として保管。score MIDI / MusicXML / PDFは後段で生成し、再生成できるようにする。
- **ADR-05 量子化の可逆性**：手動修正は別レイヤーで持ち、元のノートイベントを壊さない。メーターマップとテンポ補正もこのレイヤーに入れる。
- **ADR-06 モデル・設定差を可視化**：同じ音源に対するsmall/medium/largeの比較ログを残し、品質の優劣を印象だけで決めない。
- **ADR-07 著作物の扱い**：市販曲（Enigma Machine等）を使う場合は非公開の個人検証データとして扱い、原曲・生成MIDI・PDFを公開Gitリポジトリや一般公開ページに置かない。**市販曲を入力してよいかはPhase 1の前提条件P0で確認してから決める。**
- **ADR-08 メーターマップ（v1.1で追加）**：拍子は「小節範囲→拍子」のリストとして設定ファイルで上書きできる。自動推定結果より手動指定を優先し、score.midとMusicXMLの生成に反映する。

# 4. 処理アーキテクチャ（目標）

1. **Input**：MP3/WAV → 形式・長さ・権利の確認表示・ファイルハッシュを検査。
2. **Preprocess**：必要に応じて区間切り出し（デコード・16kHzモノラル化はMuScriptor側に任せ、重複実装しない）。
3. **Transcribe**：MuScriptor adapter → 楽器グループ別ノートイベント／raw MIDI。
4. **Timing**：ビート・テンポ・拍子の推定 → メーターマップ・テンポ補正の手動上書き → 量子化。
5. **Validate**：楽器グループ・音域・ドラムマッピング（打点のみ）・ノート長・イベント整合性・無音トラック・重複ノート・テンポの倍/半分の疑いを検査。
6. **Score**：量子化したスコアMIDI → MusicXML → MuseScoreでPDF・TAB出力。
7. **Review**：原曲と各トラックを試聴し、外部エディタで修正 → 修正データを保存して再出力。
8. **Package**：raw.mid / score.mid / score.musicxml / full_score.pdf / パート譜 / metadata.json / run.log をジョブ別フォルダに保存。

（Phase 3で追加）**Separate**：同種楽器の分離が必要な区間だけ、音源分離またはL/R・Mid/Side分離 → 再採譜 → トラック分割。

**想定ディレクトリ**：input（ローカル原曲）／intermediate（イベント・テンポ・メーターマップ）／outputs（各種MIDI・譜面）／reports（評価・ログ）。実際のパスやディレクトリ設計はClaude Code着手時に決める。

## Phase 1：PoC（技術的実現性の検証）

**目的**：検証曲の全曲で「音源→複数楽器MIDI→楽譜」の一連の変換ができるか、失敗箇所・精度・実行コストを把握する。原曲に完全一致するスコアはこの段階の目標にしない。

**実施範囲**

- [ ]  M5 / 24GBにuv・MuScriptor・MuseScore 4をセットアップし、バージョン・モデルrevision・設定を記録。
- [ ]  **30秒区間をsmall/medium/largeで採譜**し、処理時間・ピークメモリ・音符数を比較（U1・U2の一次回答）。
- [ ]  全曲をlarge（不安定ならmedium）で採譜し、楽器グループ別トラックのMIDIを保存。
- [ ]  冒頭のシンセ、バンド入り、速いユニゾン、ドラム密集、変拍子を含む15〜30秒の区間を複数特定。
- [ ]  MuScriptorのMusicXML／PDF／TAB出力を確認。テンポ・拍子・TABの問題を記録。
- [ ]  **拍子の扱いを確認**：途中で拍子が変わる区間で、自動推定と `--beats-per-bar` 指定がどう振る舞うかを記録（曲全体で1拍子のみか、区間指定できるか）。テンポの倍/半分誤検出の有無も記録。
- [ ]  **同種楽器の扱いを確認**：`muscriptor list-instruments` で分類を確認し、ギター複数・鍵盤複数が1トラックにまとまるか、ユニゾンでノートが欠けるかを記録。
- [ ]  代表フレーズの正解音符を、耳コピまたは自作MIDIのレンダリング音源で作り、mir_evalで誤検出／取り違え／欠落を分類。

**成果物**：raw.mid、score.mid、MusicXML、確認用PDF/TAB、検証レポート（楽器別問題表、速度・メモリ、モデル比較、拍子・同種楽器の挙動）、再現手順。

**完了条件（Gate P1）**

- [ ]  全曲で実際の生成MIDIを取得し、複数楽器トラックとノートデータを検査済み。
- [ ]  少なくとも1件のMusicXMLとPDFの作成を確認済み。
- [ ]  重要な失敗・未分離パート・手動補正項目を一覧化。
- [ ]  small/medium/largeの使用方針を証拠付きで判断できる。
- [ ]  拍子変更と同種楽器の扱いについて、Phase 2〜3で自前実装が必要な範囲が判断できる。
- [ ]  このゲートは「高精度達成」を意味しない。

**後回し**：独自UI、完全自動修正、全ジャンル対応、クラウド運用。

## Phase 2：MVP（最小動作プロダクト）

**目的**：Macで1コマンド（または設定ファイル）から、ローカル音源1曲を安定して変換し、成果物を同じフォルダへ出力できる。

**実施範囲**

- [ ]  Pythonプロジェクト（uv・uv.lock）、Git管理、セットアップ手順（Hugging Faceのゲート手順を含む）を用意。
- [ ]  Transcriberアダプター：モデル指定、入力、楽器指定、出力先、CPU/MPS、量子化・テンポ関連オプション、ログを設定可能にする。
- [ ]  **ジョブ設定ファイル**：モデル、BPM/固定テンポ、最初のダウンビート、量子化グリッド、**メーターマップ（小節範囲→拍子）**を書けるようにする（ADR-08）。
- [ ]  メーターマップをscore.mid／MusicXMLに反映する処理（MuScriptorが区間指定に対応していればそれを使い、非対応なら後処理で拍子記号を書き換える。どちらにするかはGate P1の結果で決める）。
- [ ]  入力検証、ファイル名・パスの安全化、ジョブID、エラーハンドリング、重複実行防止を実装。

- [ ]  ドキュメント、型チェック、ユニット／統合／回帰テストを整備。

**成果物**：同種楽器の部分分離／メーターマップ自動提案／TAB改善／バッチ処理を備えたツール、楽器別品質レポート、テストスイート。

# 6. 評価戦略・受入基準

**PoCで測る値（目標値は未確定）**

- 曲単位：処理成功率、実行秒数、最大メモリ、モデルサイズ、出力形式の妥当性。
- トラック単位：検出楽器グループ、トラック数、音符数、音域、無音／誤分類の割合、ドラム音色。
- 音符単位：正解データのある区間で、mir_evalによりpitch precision/recall/F1、onset F1（例：±50ms窓）、offset誤差を記録。ドラムはonsetのみで評価。指標と許容窓は検証対象に合わせて固定し、後から恣意的に変えない。
- 譜面単位：小節区切り、拍子、休符・タイ、TABの運指可能性、人間の修正時間。
- 参考値：モデルカードの公表値（instrument-agnostic F1、mir_eval）と同じ指標系で比べ、自分の素材での乖離を把握する。
- 重要：市販曲の完全な正解MIDIは持っていないため、F1の数値だけで正解率を断言しない。短い採譜済み区間や、自作MIDI→音源レンダリングによる既知の正解素材を組み合わせる。
- Phase 4の正式な数値KPIはPhase 1〜3の実測を見て設定する。現時点では未確定。

**固定テストケース案**：（P0-1で許可された場合）Enigma Machineの電子音イントロ／冒頭のバンドリフ／複雑なギター・キーボード／ドラムフィル。加えて、自作の単音・コード・ドラム・変拍子・テンポ変化・**ギター2本のダブリング・ユニゾン**素材を用意する。

# 7. リスク・依存関係・未決事項

## 7.1 リスク

- **R1 楽器分離／音符誤認識（高）**：歪みギターと鍵盤のユニゾン、ドラム連打、7弦の低音は取り違えやすい。さらにモデルは36グループの固定分類で、**同じ楽器・同じ音程のノートを同時に表現できない**ため、ダブリングやユニゾンは構造的に欠ける。対策は区間の再処理、楽器指定、音源分離（FR-11）、手修正。
- **R2 拍子・グリッドの誤り（高）**：変拍子や拍の取り違えは楽譜全体を崩す。テンポの倍/半分誤検出も公式に注意書きがある。途中の拍子変更への対応は文書化されていない。対策は未量子化MIDIの保全、メーターマップ（ADR-08）とテンポの手動上書き、Validatorでの倍/半分検出。
- **R3 24GBメモリでのlarge安定性（低〜中）**：largeは1.4Bパラメータ・約2.7GBで、5秒チャンク処理のため曲長でメモリが急に増えにくい見込み。ただし公式の必要メモリは未公表のため、Phase 1の30秒テストで実測し、mediumを代替にする。
- **R4 モデル重みの利用条件（高）**：NeuralNoteのコードはApache-2.0、MuScriptorのコードはMITだが、重みはCC BY-NC 4.0（主に研究目的）。さらにゲート規約で、**必要な権利のない音楽ファイルの採譜が禁止**され、利用者は権利の保証とMirelo・Kyutaiへの補償を負う。個人・非商用でも市販曲の入力が許されるとは限らない。P0-1で判断し、商用化前には別ライセンス・代替モデル・権利処理が必要。
- **R5 原曲・派生譜面の著作権（高）**：個人利用と公開／共有／頒布では許容範囲が異なる。R4の入力条件とあわせて使用目的と権利関係を確認し、無許可の音源・採譜データを公開リポジトリに含めない。
- **R6 外部依存の変化（中）**：MuScriptorは2026年公開の若いプロジェクトで、CLIのオプションや出力が変わる可能性がある。MuseScore、FFmpeg、Pythonライブラリも同様。uv.lockとモデルrevisionで固定し、固定の回帰テストで検出する。
- **R7 Demucs等の保守性（中）**：音源分離は必須ステップにせず、FR-11用の交換可能な部品として段階的に導入する。
- **R8 品質の上限（中、v1.1で追加）**：品質の上限はモデルが決め、ツール側の工夫では大きく越えられない。largeの公表Multi F1は48.2（自己申告）。「下書き＋手修正」の位置づけを保ち、修正しやすさ（区間特定・再変換）に投資する。

# 8. Claude Codeへの実装依頼順序

**原則**：Phase 1の実測が済む前に、汎用GUIや複数モデルの統合を先に実装しない。抽象化は必要になってから行う。

1. **CC-01｜環境検証とPoC計測**：uv / MuScriptor / MuseScoreの動作とライセンスの現状を確認。30秒区間をsmall/medium/largeで実行→全曲を実行し、再現可能なログと結果を残す。拍子変更・同種楽器の挙動を記録し、PoCの品質評価表を提出。（P0の権利判断とHFの同意はユーザーが事前に行う）
2. **CC-02｜MVP設計と最小CLI**：入力1ファイル→MuScriptor→raw MIDI／score MIDI／MusicXML／PDF。ジョブ設定ファイル（メーターマップを含む）、データ契約（ADR-03）、成果物ディレクトリを定義。境界はTranscriber／Validator／JobRunnerの3つ。
3. **CC-03｜検査と品質比較**：MIDIの構造検証・トラック統計・mir_evalによる音符一致率の検証スクリプト、自作の正解MIDIサンプル（ダブリング・変拍子を含む）とそのレンダリング音源を追加。
4. **CC-04｜安定化**：障害処理、モデルrevision／ツールバージョンの固定、テスト、自動生成ログ、README。
5. **CC-05｜Phase 3の機能開発**：Phase 1・2で判明した誤りの多い順に、同種楽器の分離／拍子の自動提案／TAB改善／UI／バッチ等を実装。

**Claude Code各タスクの共通DoD**

- [ ]  作業の目的と範囲が明記され、PoCでは変更を最小限にしている。
- [ ]  使ったツール／モデル／重みのバージョン・revisionと利用条件を記録。
- [ ]  実行手順、サンプル設定、期待する出力をREADMEに追記。
- [ ]  エラーケース・テスト・手動確認方法がある。
- [ ]  実行結果を過大評価せず、未検証と失敗を明記。
- [ ]  原曲MP3・生成された著作物・秘密情報（HFトークン等）をGitにコミットしない。
